## 空间与保留建议（待批准，不自动执行）

- 若 S=64 MiB，满保留加双暂存的规划量约 **1.328 GiB**；若未来 S=1 GiB约21.25 GiB；S=2 GiB约42.5 GiB将超出30GiB建议预算。当前空间明显够用，但没有增长时间序列，**不能给出真实日增长率或保证未来媒体容量**。上述阈值对应S约1.41GiB后应重新评估保留策略，不能靠删除游戏腾空间。

## 可复用工具及边界

现有 [RUNBOOK](../../tools/activation/RUNBOOK.md) 的“最新备份→独立介质→新候选”顺序可以复用，不需要新备份框架。`backend/src/cli.ts` 的 backup/verify/restore 接受显式路径，F盘可作目标：

- `createBackup`（`backend/src/database/backup.ts`）使用 SQLite backup API 捕获一致性逻辑状态（含已提交WAL内容），逐文件SHA-256、DB完整性/外键及全表指纹校验，完成后才写 manifest；不是分次裸拷贝 db/WAL/SHM。
- 媒体须显式 `--media-dir <核定目录> --media-quiesced`，并真正停写；逐文件哈希和前后清单核对。没有该参数的备份不包含媒体。当前一次只接受一个媒体根；发现多个根时分批核定，不擅自归并来源。
- `verify --backup` 校验文件长度/SHA-256、数据库完整性/指纹；`restore --backup --target` 只恢复到**不存在的新目录**并校验，保留会话/归档待核对标记，不能覆盖旧库或直接启动。
- 可复用 `tools/https-sync/check-private.ps1` 检查新私有边界，但只看目录和直接子项，深层文件仍须逐项审计；它不设置ACL。**当前工具没有BitLocker门槛、容量/保留调度或跨盘发布事务，需受控人工流程补齐**，不能只给CLI换一个F路径就宣称完整方案已生效。
- `verify/restore` 会读取私有数据进行内部完整性/指纹计算但不输出正文；SQLite只读连接也可能产生WAL/SHM伴随行为。因此本轮未运行这些工具。下一批授权须覆盖真实源的必要SQLite备份访问及新副本/恢复目录的伴随文件，不能保证源文件系统逐字节无变化。不会运行迁移、候选激活或真实服务。
