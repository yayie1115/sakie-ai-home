# Isolated HTTPS deployment: commands for the separately authorized maintenance window

Nothing in this package installs itself or edits Nginx. Source bundle stays private; never upload it to the public repository. Run only after approval for the new hostname, certificate, isolated directories/container and disposable Windows pairing. No main/www/phos changes.

## Scope
- Dedicated HTTPS origin: https://sync-check.sakiehome.icu (new A record to Seoul; AAAA must not point elsewhere). TLS must validate normally; never use -k or disable TLS verification.
- Source: /srv/sakie-sync-acceptance/release (this package). Data/WAL/SHM: /srv/sakie-sync-acceptance/data. Synthetic identity/password: /srv/sakie-sync-acceptance/identity, runtime read-only. Evidence: private /srv/sakie-sync-acceptance/evidence.
- Only new directories: data/identity owner numeric 1000:1000, 0700; generated secret files 0600. Verify container node UID=1000 and selected host account mapping before provisioning. Do not chmod/chown existing application directories.
- Dedicated Compose project sakie-sync-acceptance; only 127.0.0.1:3301 -> container 3000, internal network, no runtime egress, no model configuration. Resource settings are safety caps (384MiB, 0.5 CPU, 64 PIDs), not measured usage. Logs bounded at 2x5MiB. Restart=no intentionally; only this container is restarted by acceptance.
- Fresh synthetic cloud schema v4 and local archive v1 only. Do not copy or mount real databases/backups.

## Authorized preparation (batch; stop on failed command)
1. Record nginx -t, listeners 80/443/3301, Docker version/Compose version, current phos health, disk/memory and hashes of existing site configuration. If 3301 is occupied, project/directories exist unexpectedly, available resources are inadequate or phos baseline fails, STOP. Do not stop another service. Check image cache/build headroom; container cap does not cap image build memory.
2. Transfer the package via SSH privately, compare the .tar.gz SHA-256 with Windows, list archive paths before extraction (no absolute paths, .. or links), extract into a newly created empty release directory. Verify every manifest entry SHA-256 before build. Retain the original package and audit outputs privately.
3. Create ONLY the new data/identity directories with install -d -o 1000 -g 1000 -m 0700, plus a private evidence directory. No recursive ownership change outside this scope.
4. In release: docker compose --env-file acceptance.env -f compose.json -p sakie-sync-acceptance config --quiet; build cloud; run --rm --no-deps initialize; up -d --no-deps cloud. Initialize is one-shot and refuses an existing database/identity/marker. Do not rerun or reset it on failure. No host Node install required. Never print login-secret.txt.
5. Validate loopback health, JSON identity marker/run ID, container user/mounts/network restrictions and resource limits. API unavailable externally until the dedicated Nginx site is approved and enabled.
6. Add only the dedicated new subdomain A record. Create the new nonsecret ACME webroot /srv/sakie-sync-acceptance/acme/.well-known/acme-challenge with 0755 traversal/read permissions (no change to existing webroots). Install nginx-http.conf as a separate new port-80 vhost, nginx -t then controlled reload. Use certbot certonly --webroot -w /srv/sakie-sync-acceptance/acme -d sync-check.sakiehome.icu (not --nginx) so certificate issuance does not rewrite other vhosts. After success install nginx.conf as an additional new TLS site, nginx -t then controlled reload. Preserve the existing certbot timer and phos renewal configuration; validate renewal for only the new certificate. Keep current default and phos configurations unchanged. No websocket upgrade: /ws and every non-/api/ URL are 404. Application trust proxy remains disabled; proxy IP-based limits are conservatively shared, not bypassed via spoofed X-Forwarded-For. Do not add global proxy/CORS/trust settings.
7. Recheck phos baseline, existing site hashes, 80/443 and dedicated SNI, normal TLS validation, new health/identity marker. Capture memory/disk/docker stats as actual measurements; stop before acceptance if budgets threaten other services.

## Windows preparation and one-click acceptance (after approval)
- Authorize a NEW empty E:\sakie-ai-home-data\https-acceptance-<runId> private directory only, owned by the ordinary running user, allowing only that user, SYSTEM and Administrators. A private inheritable DACL must protect future archive/WAL/SHM/credential files. This package never applies ACLs; check-private.ps1 only checks them. Existing sensitive roots and old fixtures are excluded.
- From the project: powershell -NoProfile -File tools/https-sync/prepare-windows.ps1 -RunDirectory <private-dir> -Template <package>\windows-run.template.json
- Run the printed existing approve-production command in an interactive ordinary-user terminal and type its exact target confirmation. It binds origin, policy hash, archive and credential paths. No network at this step.
- Ensure Windows SSH alias sakie already has a verified host key and maintenance authorization for the fixed sudo -n Docker commands below. No new broad sudoers grant is implied. If sudo requires interaction or is unavailable, stop and arrange the maintenance method separately; do not change SSH/sudo policy automatically.
- One command: node tools/https-sync/accept.mjs --run <private-dir> --authorized-remote-run
- This retrieves ONLY the new synthetic login password over the existing SSH channel into process memory (not printed or persisted in Windows), verifies the HTTPS service marker before sending it, creates one disposable device, runs actual compiled Agent CLI and core, simulates client network outage and lost ACK response over HTTPS, restarts ONLY the acceptance cloud container through fixed SSH command, verifies persisted ACK/history and exact message hashes/order, revokes the device and writes sanitized result.json. Test configuration and credentials remain private. No permanent agent/service is installed.
- The script reads cloud credentials and restarts the isolated container, so do not run it before authorization. It never invokes deployment, ACL or DNS commands. Transport faults are injected locally; this is not a physical WAN outage test.

## Stop / rollback / evidence
- Any marker/TLS/identity/policy mismatch stops before credential submission; unsafe local directory is rejected. Fresh-run guards refuse previous archive/credential/result files. Exceptions preserve partial results; if device cleanup cannot be confirmed, owner revocation is a separate follow-up. Never rerun initialization or adopt a partially restored database automatically.
- On deployment faults: stop ONLY the sakie-sync-acceptance cloud service. After explicit maintenance approval disable only the new Nginx site and nginx -t/reload; revert only the new DNS record/certificate arrangement if needed. Never docker compose down -v, prune, delete data or restore onto a database. Retain all artifacts and new data for audit.
- Preserve package hash/manifest, site config before/after hashes, nginx -t and health status, loopback/public bindings, identity run ID (not credentials), actual resource readings, result.json and cloud schema/integrity/ACK read-only evidence. No cookies/token/password/request bodies in public reports.
- Docker build/Compose parsing, Nginx syntax, external DNS/TLS, internal-network host port reachability and actual SSH sudo capability still need authorized host validation. Local TLS fixture evidence does not replace these checks.
